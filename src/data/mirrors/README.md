# 镜像源数据

一个工具一个 JSON 文件，文件名即工具标识（如 `pip.json`、`debian.json`）。
以下划线开头的文件不参与构建（`_template.json` 是模板）。

新增一个工具 = 新增一个文件，不需要改任何代码。

## 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 工具标识，小写字母/数字/连字符，决定页面锚点。**全站唯一** |
| `name` | ✅ | 展示名称，如 `PyPI / pip` |
| `category` | ✅ | `language` / `system` / `container` / `other` |
| `modified_file` | ✅ | 该配置会改哪个文件（或填「环境变量」）。读者动手前要能看到这个 |
| `note` | | **工具级**说明，对该工具所有镜像源都成立 |
| `mirrors` | ✅ | 至少一条，见下 |

`note` 分两级：各源完全相同的注意事项（如「执行前先注释掉旧 sources.list」）
写在工具级，只对某个源成立的写该源的 `note`。判断标准很简单——一句话如果会
随源的个数重复十几遍，它就属于工具级。

每条 `mirrors` 的字段：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `station` | ✅ | 镜像站名，如 `清华 TUNA` |
| `endpoint` | ✅ | 实际镜像地址，用于展示 |
| `doc` | | 官方帮助页 URL，必须能打开 |
| `status` | ✅ | `ok` 可用 / `degraded` 有限制 / `dead` 已停用 |
| `verified_at` | ✅ | 最后人工核实日期，`YYYY-MM-DD` |
| `snippet` | ✅ | 可直接粘贴的完整命令。多行用 `\n` |
| `note` | | 需要提醒的坑 |

## 几条硬规矩

1. **`verified_at` 必须真实**。这是整个站点的可信度来源，填一个没核实过的日期
   等于骗人。
2. **`snippet` 照抄官方文档**，不要自己改写语法。各工具语法差异很大，
   改一处就可能让人贴进终端报错。
3. **数据来源只用镜像站官方文档或其端点**。不要抄搜索引擎里的博客——
   这类文章大量自称「最新实测」，实测内容互相矛盾。
4. 镜像站已停止某项服务时，**不要直接删掉那条**，改成 `status: "dead"`
   并保留。读者 dotfiles 里往往还躺着过期配置，需要能对上号。
5. 加数据前先想一下：这条是正确的吗，还是只是「我记得是这样」？后者一律
   去核实，核实不了就不写。

## 校验

构建时会用 zod 逐字段校验。字段缺失、日期格式不对、`status` 取值非法都会让
`npm run build` 失败并指出是哪个文件的哪个字段，不会静默发布坏数据。
