# 镜像源数据

一个工具一个 JSON 文件，文件名即工具标识（如 `pip.json`），决定页面地址 `/mirrors/<id>/`。
以下划线开头的文件不参与构建（`_template.json` 是模板，可复制起手）。

**新增一个工具 = 新增一个文件，不需要改任何代码。**

## 收录范围：官方源 + 国内源

只收两类：各工具的官方源（`region: "official"`），以及国内的公共镜像站。
国外镜像站一律不收——本站叫「国内镜像源」，混进 RIKEN、KAIST、OVH 这类源只会让下拉变长。

## 核心：命令只写一遍

数据分三层，为的是让**命令正文在工具级只出现一次**：

```
工具级  variants —— 命令模板，正文里用 {变量} 留空
版本级  versions —— 只填随发行版变化的变量（Debian 的套件名 suite）
源级    vars     —— 每个源只填变量值
```

最终的命令是「版本 × 源」的组合：模板一份，两层各填一部分变量。变量越具体越优先：

```
工具级 var_defaults  <  版本级 vars  <  源级 vars
```

不这样组织的话，Debian 的「2 个版本 × 10 个源」会各存一份 26 行的配置，
彼此只差 2 个 URI 和套件名——20 份、15.2KB 的命令正文，而整个数据文件现在只有 4.0KB。
把套件名提成 `{suite}` 之后，**支持一个新版本只需要在 `versions` 里加 4 行**——
源一条都不用改，因为各源在两个版本下的地址是同一个。

## 工具级字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 小写字母/数字/连字符。**决定页面 URL**，且不能取 `index`（会和索引页冲突） |
| `name` | ✅ | 展示名称，如 `PyPI / pip`。**有版本的工具只写工具名**（`Debian`），版本由下拉体现 |
| `category` | ✅ | `language` / `system` / `container` / `other` |
| `icon` | ✅ | 单个 emoji。别用 ZWJ 组合序列，各平台渲染不一致 |
| `tagline` | ✅ | 一句话说明，索引页卡片与工具页面包屑用 |
| `endpoint_var` | ✅ | 哪个变量是「主地址」。`{host}` 由它推导 |
| `variants` | ✅ | 命令变体，至少一条。见下 |
| `versions` | | 发行版本。不写 = 该工具没有版本之分（如 pip），页面不出版本下拉 |
| `var_defaults` | | 工具级变量默认值，各源自动带上，版本级与源级可覆盖 |
| `modified_file` | ✅ | 该配置会改哪个文件（或「环境变量」）。**目前不入 UI**，留作数据出处 |
| `note` | | **工具级**说明，对该工具所有源都成立。**目前不入 UI**，留作数据出处 |

### `versions[]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key` | ✅ | 版本标识，如 `13`。只能小写字母和数字。进深链与 DOM id，工具内唯一 |
| `label` | ✅ | 展示名，如 `13 (trixie)`。版本下拉里显示的就是它 |
| `vars` | | 该版本独有的变量，如 `{"suite": "trixie"}`。被源级同名变量覆盖 |

按展示顺序排列，**第一项是默认**（新版本在前）。版本之间只应差变量，不要各写一份命令。

### `variants[]`

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key` | ✅ | 变体标识，进 DOM id，工具内唯一 |
| `lang` | ✅ | 语言标签，展示在命令块左上角，如 `bash`、`ini`、`toml` |
| `label` | ✅ | 展示标签，如「写入 deb822 源文件」「永久配置」。自由文案 |
| `code` | ✅ | 命令模板，含 `{变量}`。**照抄官方文档**，不要自己改写语法 |
| `note` | | 只对该变体成立的一句话 |

变体数量随工具不同而不同——Debian、Ubuntu、pip 目前各只有 1 种。不要强凑成固定的几个。

## 源级字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `station` | ✅ | 镜像站名，如 `清华 TUNA`。同工具内唯一。它同时是深链 slug 的来源 |
| `vars` | ✅ | 变量表，至少含 `endpoint_var` 指向的那个 |
| `status` | ✅ | `ok` 可用 / `degraded` 有限制 / `dead` 已停用 |
| `verified_at` | ✅ | 最后人工核实日期，`YYYY-MM-DD` |
| `region` | | `official` 官方 / `cn` 国内。**缺省 `cn`**，决定来源下拉里的分组 |
| `doc` | | 官方帮助页 URL，必须能打开。**目前不入 UI**，留作数据出处 |
| `note` | | 只对该源成立的提醒。**会在命令块上方渲染** |
| `skip_variants` | | 该源不适用的变体 key。**只能少一块，不能改写正文** |

**状态标签已经不在页面上显示了**，`status` 只影响已停用源的整体淡化。所以
`degraded` / `dead` 的源必须在 `note` 里写清楚为什么——否则读者看不出差别，
会直接把一份失效的配置贴进终端。

## 模板语法

| 写法 | 含义 |
| --- | --- |
| `{name}` | 占位符，`name` 为小写字母/数字/下划线，值从变量表取 |
| `{{` `}}` | 转义，输出字面量的花括号 |
| 其它 `{` `}` | **报错**，不会静默放过 |

变量值里可以引用其它变量，如 `"sec": "{deb}-security"`，或 `Suites: {suite}-backports`
这样在占位符后面接字面文字。这样各源只需填一个 `{deb}`——而「安全更新 URI 写错导致
`apt update` 报错」这个最容易出错的坑就被结构性消除了。
主地址（`endpoint_var` 指向的那个）**必须是字面 URL**，不能由变量拼——它是推导的根。

`{host}` 由主地址自动推导（`https://mirrors.x.edu.cn/debian` → `mirrors.x.edu.cn`），
不必也不该写进 `vars`。

## 几条硬规矩

1. **`verified_at` 必须真实**。这是整个站点的可信度来源，填没核实过的日期等于骗人。
2. **`code` 照抄官方文档**，不要自己改写语法。各工具语法差异极大，
   改一处就可能让人贴进终端就报错。
3. **数据来源只用镜像站官方文档或其端点**。不要抄搜索引擎里的博客——
   这类文章大量自称「最新实测」，实测内容互相矛盾。
4. **不要凭空加 `trusted-host` 之类的「保险」参数**。它让 pip 跳过该主机的证书校验，
   等于把一个本来安全的 HTTPS 源降级。官方文档没写就不要加。
5. 镜像站已停止某项服务时，**不要删掉那条**，改成 `status: "dead"` 并保留，
   同时在 `note` 里写明。读者 dotfiles 里往往还躺着过期配置，需要能对上号。
6. 加数据前自问：这条是核实过的，还是「我记得是这样」？后者一律去核实，核实不了就不写。
   新增版本同理——要**逐源**确认它确实还有这个发行版的数据（见第 4 节的检查）。

## 检查

构建时执行，任一不通过都会让 `npm run build` 失败并指出位置，不会静默发布坏数据：

1. **`[字段]`** —— zod 逐字段校验。字段缺失、日期格式、`status` / `region` 取值、
   变体 key 或版本 key 重复、`skip_variants` 指向不存在的变体、`station` 重复、
   主地址不是合法 URL（版本级覆盖的也算），都会报出。
2. **`[模板]`** —— 占位符替换，逐「版本 × 源」组合跑一遍。模板只有一份，一个占位符写错
   会同时命中十几个组合，所以报错按「版本 / 变体 / 问题」分组、折叠受影响的源，
   并区分「所有源都缺」（模板写错）、「某版本下所有源都缺」（该版本的 vars 漏了）
   与「个别源缺」（数据漏填）。
